# JPEG C 路修复后板测（2026-10-04）

## 位流与环境

用户手动综合、布局布线并烧录 20:37 生成的 `fpga_prj_jpeg_Runs/best_result/fpga_prj_jpeg.bit`。RK 重新枚举 PCIe 后，BAR JPG3 和首次故障寄存器 `0xEC` 均可读。TD 布局报告 JPEG 200 MHz 时钟 SWNS **+0.019 ns**、STNS 0，整机 253/272 ERAM、93/240 DSP。时序已达到非负放行门槛，但裕量很小；更换布局条件或温度时需要复核。

此前位流 C 路输入桥报错、无 EOI、零帧。本位流仅将 C 输入 FIFO 从 256 加深到 512 个 72-bit 字，同时增加首次故障原因/位置诊断。上板后 C 正常，实际效果与输入缓冲不足的假设一致；旧位流未记录具体 cause，因此不能仅凭对比证明原故障一定是 FIFO 满。

## 功能采集

- Q85、灰度 HDMI 同时运行时，RK 成功采集并解码 10 组 A/B/C 1920×360 单色 JPEG，并生成 10 张 1920×1080 PGM。第一组 A/B/C 为 84,843/84,583/84,496 字节。文件位于 RK `/root/jpeg_rk/jpeg_latest_q85/`。
- 三路文件经 `file` 确认为 JFIF baseline、8 bit、单通道 1920×360；PGM 确认为 1920×1080。10 张 PGM 的抽样相邻行平均绝对差：带内 2.67，A/B 接缝 3.42、B/C 3.38、C/A 3.37，未出现明显数量级更大的条带跳变。这是数值检查，不能替代人工观察画面。
- Q50 时，修复 RK GStreamer `Gst.Sample` 回调调用方式后，成功解码并重建 3 组；第一组 A/B/C 为 37,509/37,080/36,894 字节，位于 `/root/jpeg_rk/jpeg_latest_q50_fixed/`。一次较早的 Q50 采集因 RK Python GI 回调间歇性方法查找异常而未保存文件，当时 FPGA A/B/C 计数仍同步且故障 0；该接收端问题已在源码中修正并用后续 Q50、Q85 采集验证。
- 最终再次 Q85 采集 3 组，A/B/C 均解码并拼接成功，位于 `/root/jpeg_rk/jpeg_q85_final/`。

## 当前状态与边界

测试结束恢复 Q85、预处理模式 3，C 驱动 `recover_on_error=1`，灰度 HDMI 进程仍运行。功能性 JPEG 压缩传输、三路接收解码及 1080p 重建已上板验证。

采集脚本收尾时，GStreamer 分别停止三台 V4L2 设备。旧 RK 驱动把此期间的 C DMA 等待超时当成 FPGA 故障，导致一次正常采集后 BAR 帧数清零。已将 C 自动复位条件限制为 FPGA BAR 真正报告 JPEG fault，并在板端重新编译加载。最终 Q85 再抓取 3 组完整 1080p 图，停止采集后 BAR 仍保留 A/B/C=`6/6/6`、`faults=0`，见 RK `/root/jpeg_rk/jpeg_driver_final2/`。

尚未做 10 分钟以上老化和实际道路裂缝识别指标测试；A/B/C 仍按接收时间戳配对，协议没有共同硬件帧号，单路丢帧时可能误配。
